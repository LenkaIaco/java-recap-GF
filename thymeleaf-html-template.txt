/* 
MVC workflow with Thymeleaf:
1. Spring MVC: arrived HTTP request, parses it: URL parameters, form fields, JSON... converting into java objects(via @ModelAttribute, converters, data binding) and routing it to the appropriate controller + endpoint method. Controller method returns a Model(Spring-constructed) and a view name. ViewResolver finds the view html template.
2. Thymeleaf is a templating engine responsible for 
	translating from Java Objects into html data in html templates (based on which object references are stored in model attributes, and which htmltemplate the ViewResolver points out)
	and vice versa from HTML templates into Java Objects 
	constructing the final html page including parameters from java objects, css styling, javascript, images 


3. Spring MVC: passing the HTML result to the HTTPResponse objects(Jakarta Servlet implementation like Tomcat, Jetty, ...)

saved in spring applications under src/main/resources/templates:

 Spring boot templates(thymeleaf, freemarker etc) have a default template location, they expect classpath:/templates/ . Spring boot standardizes this into src/main/resources/templates, which the ViewResolver scans to locate the html templates

There are other folders automatically searched inside the classpath, apart from templates: 
Spring boot looks into classpath, for folders: 
classpath:/static/
classpath:/public/
classpath:/resources/
classpath:/META-INF/resources/
classpath:/templates/
 --------------------------------------------
Classpath is a RUNTIME reference, not a source-folder-type structure:
- runtime root(if app runs via IntelliJ, 'classpath' is decided by IntelliJ who gives java -cp or -classpath command),
   If I run a java command manually, classpath becomes the folder specified in the command, 
   e.g. for running MyApp.class from 'parent' folder + including all dependencies from myfolder/resources:
	java -cp .;myfolder/resources MyApp
- When app is run via IntelliJ, 'classpath' is decided by IntelliJ who issues java -cp or -classpath command.
   Classes from src/main/java are compiled + resources from src/main/resources are copied. 
   These files are then automatically included into the classpath folder: out/production/<module>. 
   This becomes the classpath root because IntelliJ launches the JVM with:  -classpath out/production/<module> + dependencies 
   Example (Windows):
	java -cp out\production\MyModule;all-dependencies; lib\* com.example.MyApplication
--------------------------------------------
So, the classpath ends up containing:
out/production/<module>/
    com/example/...        ← compiled Java classes
    static/                ← copied from src/main/resources/static
    templates/             ← copied from src/main/resources/templates
    application.properties ← copied from src/main/resources

Apart from out/production/<module>, classpath contains dependencies, resolved at runtime based on what dependencies are in maven/gradle cache for this projects + locations that store these locations:

-classpath out/production/<module>;
  C:\Users\<you>\.m2\repository\spring-boot\spring-boot-3.2.0.jar;
  C:\Users\<you>\.m2\repository\spring-core\spring-core-6.1.0.jar;
  C:\Users\<you>\.m2\repository\thymeleaf\thymeleaf-3.1.0.jar;
  ... many more ... 

Copying dozens or hundreds of JARs into your project would be wasteful. So IntelliJ just builds a long -cp argument with references to the jar location, which enables jars to be shared accross multiple projects.
*/


/* html pre-generated template header and body structure in intellij - click on templates - new - html template
pre-header xmlns disclaimer tells to HTML parser to use thymeleaf namespace (every abbreviation th:* in this document refers to using thymeleaf's internal syntax rules. http://www.thymeleaf.org is just an unique ID, it does not fetch any content from the url connected to the th: references). Thymeleaf attributes: 
	th:object for translating @ModelAttribute, or model.addAttribute("attr", myobject): 
	  It has to be sourced from MVC bound to an endpoint that contains that object and sends it to the html template containing th:object. 
	  So either from automatically-translated @ModelAttribute from the URI, or manually adding it in method body: model.addAttribute("attr", myObject)
	th:text, 
	th:each for processing collections, 
	th:if, th:unless, th:switch + th:case for conditions, 
	th:href, th:src for formatting chosen text as a chosen html link (dynamic URLs), 
	th:replace, th:insert for template fragments and layouting

<p th:if="${validationResult != null && #strings.contains(validationResult,'not')}" th:style="|color: red|" th:text="${validationResult}"></p>
<p th:unless="${validationResult != null && #strings.contains(validationResult,'not')}" th:style="'color: green'" th:text="${validationResult}"></p>

<div th:if="${fox == null || fox.getTricks().isEmpty()}">
    <p>No tricks learned yet</p>
</div>

*/

head change - link css related + thymeleaf
-------------------------------------------------

Fragment html files are pieces of html set aside because they repeat on multiple html pages, so to avoid redundancy, they get referenced from another time.

fragment file: starts with th:fragment and gets referred to in other html files with th:replace="fragmentFile::section"

no head, no body, first element is always fragment:

<nav th:fragment="navigation">
   or 
<ul th:fragment="navigationLinks">

   and possibly, other fragments:

<form th:fragment="loginForm" action="/login" method="post">

-------------------------------------------------

Path Variable syntax:  "/filter/only%20available"

    <a th:href="@{/filter/{filterButton}(filterButton='only available')}" th:class="navElements"> ONLY AVAILABLE</a>

Request Parameter syntax: "/information?usernameLogin=Lenka"

<form action="/information"
      th:action="@{/information(usernameLogin=${usernameLogin})}"
      method="post">

="@{/filter/{filterButton}('only available')}"
="@{/info(usernameLogin=${usernameLogin})}"
